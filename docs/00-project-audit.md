## 2. Суть продукта

Fastik - fullstack веб-приложение для организации сотрудничества между заказчиками и разработчиками программного обеспечения.

Продуктовая идея шире обычной биржи:

- биржа заказов;
- профили исполнителей;
- отклики;
- коммуникация;
- моковая система гаранта;
- финансы;
- аналитика;
- модерация;
- RPG-система надежности и роста исполнителя.

Главная отличительная фича - уровень исполнителя как понятная, проверяемая метрика доверия.

## 3. Целевая аудитория

Основной рынок: Россия и русскоязычный сегмент.

Основные пользователи:

- заказчики, которым нужно быстро и безопасно найти исполнителя;
- исполнители, которым нужно доказать надежность и получать больше заказов;
- администраторы и модераторы, которые поддерживают качество площадки.

## 4. Роли

Роли стоит разделить так:

- `guest` - просмотр публичных страниц, поиск, регистрация;
- `customer` - создание заказов, выбор исполнителей, оплата через мок-гарант;
- `performer` - профиль, портфолио, отклики, выполнение заказов, рост уровня;
- `support` - помощь пользователям, просмотр обращений и споров;
- `moderator` - модерация заказов, профилей, конкурсов, жалоб;
- `admin` - управление платформой, категориями, пользователями, финансами;
- `super_admin` - полный доступ, управление администраторами и системными настройками.

Риск:

Слишком много ролей может раздуть первый этап. Для MVP лучше реализовать роли в базе и middleware сразу, но интерфейсы админских ролей развивать постепенно.

## 6. RPG-система исполнителей

Это главная фича Fastik и ее нужно проектировать не как украшение, а как механизм доверия.

Предлагаемая модель:

- `XP` - очки опыта за действия;
- `Level` - уровень исполнителя;
- `Badges` - значки за достижения;
- `Roadmap` - визуальная дорога роста;
- `Requirements` - условия перехода на следующий уровень;
- `Verification` - проверки профиля, портфолио, навыков, интервью;
- `Penalties` - снижение доверия за отмены, споры, нарушения.

Пример уровней:

- `Level 1: Новичок` - заполнен базовый профиль;
- `Level 2: Исполнитель` - добавлено портфолио и навыки;
- `Level 3: Проверенный` - выполнены первые заказы без споров;
- `Level 4: Надежный` - высокий рейтинг, стабильная история;
- `Level 5: Профи` - подтвержденные навыки, высокий рейтинг;
- `Level 6: Fastik Elite` - интервью с HR/платформой и ручное подтверждение.

Важно:

Сам уровень не должен быть единственным фактором ранжирования. Иначе новые исполнители не смогут стартовать. Нужны отдельные зоны для новичков и фильтры заказчика.

## 7. Конкурсы

Идея конкурсов сильная, но рискованная по объему.

Полезный якорь для заказчика:

- заказчик получает несколько концепций/решений;
- платит призовой фонд через мок-гарант;
- выбирает победителя;
- может дополнительно нанять участника после конкурса.

Полезный якорь для исполнителя:

- конкурсы дают XP;
- победа дает бейдж и рост доверия;
- участие доступно по уровню, но часть конкурсов должна быть открыта новичкам;
- конкурс можно добавить в портфолио после завершения.

Рекомендация:

Конкурсы делать не в первом блоке. Сначала нужна стабильная база заказов, откликов, профилей, чата и статусов.

## 8. Деньги и гарант

Требование: все деньги моковые, потому что это дипломный проект.

Для диплома лучше реализовать:

- моковый баланс пользователя;
- моковое пополнение;
- резервирование средств по заказу;
- удержание средств в гаранте;
- перевод исполнителю после принятия работы;
- возврат заказчику при отмене/споре;
- история транзакций;
- админское разрешение споров.

Интеграция с demo Tinkoff API возможна как дополнительный слой, но не должна блокировать основной проект.

Риск:

Реальные платежные интеграции часто требуют актуальной документации, учетных данных, договоров и могут отнять слишком много времени. Для диплома моковая финансовая модель выглядит убедительнее и стабильнее.

## 9. Модерация

Предлагаемая логика:

- новые или непроверенные заказчики проходят модерацию заказов;
- проверенные заказчики или пользователи с подпиской публикуют быстрее;
- подозрительные заказы отправляются на проверку;
- модератор может скрыть заказ, профиль, услугу, конкурс;
- админ может заблокировать пользователя;
- support участвует в спорах и обращениях.

## 11. Стек-аудит

Выбранный стек:

- Vue;
- TypeScript;
- Tailwind CSS;
- Express;
- PostgreSQL;
- REST;
- Swagger;
- Docker;
- VPS.

Вопрос ORM:

Пожелание - без ORM. Это возможно, но требует дисциплины:

- миграции через SQL;
- запросы через `pg`;
- отдельный query слой;
- ручная типизация DTO;
- аккуратная работа с транзакциями.

Рекомендация:

Использовать `pg` + SQL migrations. Это проще объяснить на защите, чем тяжелый ORM, и хорошо показывает понимание базы данных.

Риск:

Полностью ручной SQL увеличивает объем кода. Нужно держать структуру простой и не пытаться сделать универсальный query builder.

## 12. Архитектура

Требование: frontend и backend отдельно.

Предлагаемая структура:

```text
apps/
  web/
    Vue frontend
  api/
    Express backend
packages/
  shared/
    shared TypeScript types and constants
infra/
  docker/
docs/
  architecture, diagrams, audit
```

Даже при разделении frontend/backend можно оставить их в одном репозитории как монорепо с отдельными приложениями. Это удобнее для диплома, запуска и истории коммитов.

Если нужно строго отдельно, можно сделать:

```text
frontend/
backend/
shared/
docs/
```

Рекомендация:

Для читаемости выбрать `frontend/`, `backend/`, `shared/`, `docs/`. Это проще для защиты и не выглядит слишком корпоративно.

## 17. Главные риски

### Scope creep

Проект почти production-уровня за примерно 3 недели. Риск высокий.

Митигировать:

- делать вертикальными срезами;
- не распыляться на OAuth/Tinkoff/темную тему до стабильного MVP;
- постоянно иметь рабочую версию.

### Слишком сложная RPG-система

Если начать с нее, можно застрять.

Митигировать:

- сначала сделать простую модель XP/level;
- затем добавить roadmap;
- затем бейджи;
- затем интервью и ручную проверку.

### Чат и realtime

Realtime может усложнить backend.

Митигировать:

- первый вариант сделать через REST polling;
- затем добавить WebSocket/Socket.IO, если останется время.

### Финансы

Платежи могут раздуть проект.

Митигировать:

- моковый баланс и escrow как основной сценарий;
- Tinkoff demo только как дополнительная демонстрационная интеграция.

### Отсутствие ORM

Ручной SQL дает контроль, но повышает шанс ошибок.

Митигировать:

- простые SQL migrations;
- repository слой;
- seed-данные;
- транзакции для финансовых операций.
